GOAL
----
- Understand exactly what job Go does in this repo.
- Decide honestly whether anything is better than Go for that job.
- Pick the option that best fits YOUR goal (learning C++ as a Python dev).
- Have working starter code for the main options.


--------------------------------------------------------------------------------
1. WHAT GO DOES HERE
--------------------------------------------------------------------------------

  1. HTTP API for the frontend (routing, JSON, CORS)
  2. Process supervision: start one C++ engine per symbol, wait until it's
     ready, health-check it, kill it on shutdown
  3. Routing: symbol -> engine URL
  4. Parallel fan-out: send batches to every engine at once, wait for all
  5. Order id assignment (an atomic counter)
  6. Random order generation for simulations

  Is Go good at this? Yes, genuinely. Goroutines, a great standard HTTP
  library, easy process control, and a single static binary. For THIS job,
  no language is objectively better than Go.

  But YOUR goal is to learn C++, and you already know Python. That changes
  the answer: every hour spent learning Go is an hour not spent on C++.


--------------------------------------------------------------------------------
2. THE OPTIONS
--------------------------------------------------------------------------------

  Option                          Better than Go for you?   Why
  ------------------------------  ------------------------  -------------------------
  A. Python + pybind11            YES, best learning value  C++ engine runs INSIDE
     (in-process)                                           Python. No HTTP hop.
                                                            Teaches C++/Python interop.
  B. Python FastAPI gateway       YES, if you want the      Same architecture as the
     (multi-process)              distributed design        repo, zero new language.
  C. Pure C++ gateway             YES, for maximum C++      Threads, sockets, process
     (Asio, binary protocol)      practice                  control in C++. Hardest.
  D. TypeScript (Node + Hono)     Neutral                   One language across the
                                                            frontend and gateway.
  E. Rust (axum + tokio)          No, not right now         Two hard languages at once.
                                                            Great AFTER C++.
  F. Elixir (Phoenix + OTP)       Niche but interesting     Supervisors restart crashed
                                                            engines automatically,
                                                            which is exactly what
                                                            manager.go hand-rolls.

  MEASURED WHILE WRITING THIS COURSE (on this Mac; your numbers will vary):
    Pure C++: the lesson 14b order book, -O2, no I/O: 2,000,000 random
              orders in ~230-250 ms. That's ~8 million orders/sec, about
              0.12 microseconds per order. (Harness in lesson 16.)
    Option A: 20,000 random orders matched in ~18 ms, including Python's
              per-call overhead. That's under 1 microsecond per order.
    Option B: 400 orders to one already-running engine took ~8 ms, using
              the repo's own C++ engine over HTTP. That's ~20 microseconds
              per order: about 20x slower than Option A, and over 100x
              slower than pure C++. The matching code is not the
              difference.
  That comparison is lesson 13's point: the architecture decides the speed.


--------------------------------------------------------------------------------
3. OPTION A: PYTHON CALLS C++ DIRECTLY (RECOMMENDED)
--------------------------------------------------------------------------------

Your C++ library (lesson 14 / 14b) becomes a Python module:
    import orderbook
    book = orderbook.Orderbook()

pybind11 generates the glue. You write a small C++ file describing what
to expose. (nanobind is a newer, lighter alternative by the same author.)

bindings/bindings.cpp  (compiled and tested with pybind11 3.1)
--------------------------------------------------------------
#include <pybind11/pybind11.h>
#include <pybind11/stl.h>

#include "orderbook/orderbook.hpp"

namespace py = pybind11;

PYBIND11_MODULE(orderbook, m) {
    py::enum_<Side>(m, "Side")
        .value("Buy", Side::Buy)
        .value("Sell", Side::Sell);

    py::enum_<OrderType>(m, "OrderType")
        .value("GTC", OrderType::GoodTillCancel)
        .value("FAK", OrderType::FillAndKill);

    py::class_<Trade>(m, "Trade")
        .def_readonly("buy_id", &Trade::buyId)
        .def_readonly("sell_id", &Trade::sellId)
        .def_readonly("price", &Trade::price)
        .def_readonly("quantity", &Trade::quantity)
        .def("__repr__", [](const Trade& t) {
            return "Trade(buy=" + std::to_string(t.buyId) + ", sell=" + std::to_string(t.sellId) +
                   ", " + std::to_string(t.quantity) + " @ " + std::to_string(t.price) + ")";
        });

    py::class_<Orderbook>(m, "Orderbook")
        .def(py::init<>())
        .def("add",
             [](Orderbook& book, OrderId id, Side side, OrderType type, Price price, Quantity qty) {
                 return book.add(Order{id, side, type, price, qty});
             },
             py::arg("id"), py::arg("side"), py::arg("type"), py::arg("price"), py::arg("quantity"))
        .def("cancel", &Orderbook::cancel)
        .def_property_readonly("best_bid", &Orderbook::bestBid)
        .def_property_readonly("best_ask", &Orderbook::bestAsk)
        .def("__len__", &Orderbook::size);
}

  pybind11/stl.h converts std::vector -> list and std::optional -> None
  automatically.

WHAT IT LOOKS LIKE FROM PYTHON (real output)
    >>> book.add(id=1, side=ob.Side.Sell, type=ob.OrderType.GTC, price=100, quantity=5)
    []
    >>> book.add(id=2, side=ob.Side.Buy, type=ob.OrderType.GTC, price=101, quantity=8)
    [Trade(buy=2, sell=1, 5 @ 100)]
    >>> book.best_bid, book.best_ask, len(book)
    (101, None, 1)
    >>> book.add(id=3, ..., quantity=-1)
    TypeError      <- pybind11 refuses a negative number for the unsigned
                      Quantity parameter. The C++ types protect you.

BUILDING IT

  Quick way, no CMake (this exact command was used for the test above):
    python3 -m venv .venv && .venv/bin/pip install pybind11
    PBI=$(.venv/bin/python -c "import pybind11; print(pybind11.get_include())")
    PYI=$(.venv/bin/python -c "import sysconfig; print(sysconfig.get_paths()['include'])")
    SUF=$(.venv/bin/python -c "import sysconfig; print(sysconfig.get_config_var('EXT_SUFFIX'))")
    clang++ -std=c++20 -O2 -shared -fPIC -undefined dynamic_lookup \
        -I"$PBI" -I"$PYI" -Iinclude \
        src/orderbook.cpp bindings/bindings.cpp -o "orderbook$SUF"
    .venv/bin/python -c "import orderbook; print(orderbook.Orderbook())"

  (-shared = build a shared library, -fPIC = position-independent code,
  -undefined dynamic_lookup = let Python supply its own symbols at load
  time on macOS.)

THE FASTAPI APP  (tested with FastAPI's TestClient)
---------------------------------------------------
import itertools
import random
import threading
import time

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

import orderbook as ob

app = FastAPI()
books: dict[str, ob.Orderbook] = {}
order_ids = itertools.count(1)
lock = threading.Lock()

SIDES = {"BUY": ob.Side.Buy, "SELL": ob.Side.Sell}
TYPES = {"GTC": ob.OrderType.GTC, "FAK": ob.OrderType.FAK}


class TradeIn(BaseModel):
    symbol: str
    side: str
    type: str = "GTC"
    price: int
    quantity: int


class StockConfig(BaseModel):
    symbol: str
    numBids: int
    numAsks: int
    priceMin: int
    priceMax: int
    quantityMin: int
    quantityMax: int


def trade_to_dict(t: ob.Trade) -> dict:
    return {"buyId": t.buy_id, "sellId": t.sell_id, "price": t.price, "quantity": t.quantity}


@app.post("/order/trade")
def trade(req: TradeIn):
    side, kind = SIDES.get(req.side), TYPES.get(req.type)
    if side is None or kind is None or req.quantity <= 0:
        raise HTTPException(400, "invalid side, type, or quantity")
    with lock:
        oid = next(order_ids)
        book = books.setdefault(req.symbol, ob.Orderbook())
        trades = book.add(id=oid, side=side, type=kind, price=req.price, quantity=req.quantity)
        return {
            "orderId": oid,
            "trades": [trade_to_dict(t) for t in trades],
            "bestBid": book.best_bid,
            "bestAsk": book.best_ask,
        }


@app.post("/order/simulation")
def simulation(stocks: list[StockConfig]):
    rng = random.Random()
    results = []
    with lock:
        for s in stocks:
            book = books[s.symbol] = ob.Orderbook()
            orders = [
                (next(order_ids), side, rng.randint(s.priceMin, s.priceMax),
                 rng.randint(s.quantityMin, s.quantityMax))
                for side, n in ((ob.Side.Buy, s.numBids), (ob.Side.Sell, s.numAsks))
                for _ in range(n)
            ]
            rng.shuffle(orders)
            start = time.perf_counter()
            trades = [t for oid, side, price, qty in orders
                      for t in book.add(id=oid, side=side, type=ob.OrderType.GTC,
                                        price=price, quantity=qty)]
            elapsed_ms = (time.perf_counter() - start) * 1000
            results.append({
                "symbol": s.symbol,
                "tradesExecuted": len(trades),
                "volumeTraded": sum(t.quantity for t in trades),
                "remainingOrders": len(book),
                "bestBid": book.best_bid,
                "bestAsk": book.best_ask,
                "matchingMs": round(elapsed_ms, 3),
            })
    return results

  Run it:  .venv/bin/pip install fastapi uvicorn
           .venv/bin/uvicorn app:app --port 8000

  WHY THE LOCK? FastAPI runs plain "def" endpoints on a thread pool, so
  two requests CAN run at the same time. Right now pybind11 holds Python's
  GIL during every C++ call, which happens to serialize them. But the
  moment you add py::call_guard<py::gil_scoped_release>() to a binding (so
  C++ can run in parallel with Python), two threads could be inside the
  same Orderbook at once: a data race (lesson 11). The lock makes the
  safety explicit, so it doesn't depend on the GIL.

  NOTE: "matchingMs" includes Python loop overhead, one C++ call per
  order. Exercise 2 moves the loop into C++.

  YOU CAN KEEP THE REPO'S FRONTEND: point frontend/src/lib/api.ts at this
  server, and adjust the response shape to match frontend/src/lib/types.ts.

4. OPTION B: PYTHON GATEWAY, SAME MULTI-PROCESS DESIGN
--------------------------------------------------------------------------------

A replacement for manager.go + balancer.go + Simulation.go. Tested
against the repo's own C++ engine: three engines spawned concurrently,
batches sent in parallel, engines reused on the second run, and all
processes killed on shutdown.

import asyncio
import itertools
import os
import random
import time
from contextlib import asynccontextmanager

import httpx
from fastapi import FastAPI
from pydantic import BaseModel

ENGINE = os.environ.get("ENGINE_PATH", "./engine_server")

client = httpx.AsyncClient(timeout=10)
ports = itertools.count(6060)
order_ids = itertools.count(1)
engines: dict[str, asyncio.Task] = {}
processes: list[asyncio.subprocess.Process] = []


async def spawn(port: int) -> str:
    proc = await asyncio.create_subprocess_exec(
        ENGINE, str(port),
        stdout=asyncio.subprocess.DEVNULL, stderr=asyncio.subprocess.DEVNULL)
    processes.append(proc)
    url = f"http://127.0.0.1:{port}"
    for _ in range(50):
        try:
            if (await client.get(f"{url}/status")).status_code == 200:
                return url
        except httpx.TransportError:
            pass
        await asyncio.sleep(0.1)
    proc.kill()
    raise RuntimeError(f"engine on port {port} never became ready")


async def engine_url(symbol: str) -> str:
    task = engines.get(symbol)
    if task is None:
        task = engines[symbol] = asyncio.create_task(spawn(next(ports)))
    return await task


@asynccontextmanager
async def lifespan(app: FastAPI):
    yield
    for proc in processes:
        proc.kill()
    await client.aclose()


app = FastAPI(lifespan=lifespan)


class StockConfig(BaseModel):
    symbol: str
    numBids: int
    numAsks: int
    priceMin: int
    priceMax: int
    quantityMin: int
    quantityMax: int


def make_orders(s: StockConfig) -> list[dict]:
    rng = random.Random()
    return [
        {"orderid": next(order_ids), "book": s.symbol, "tradetype": "GTC", "side": side,
         "price": rng.randint(s.priceMin, s.priceMax),
         "quantity": rng.randint(s.quantityMin, s.quantityMax)}
        for side, n in (("BUY", s.numBids), ("SELL", s.numAsks))
        for _ in range(n)
    ]


async def run_batch(s: StockConfig) -> dict:
    url = await engine_url(s.symbol)
    await client.post(f"{url}/reset")
    resp = await client.post(f"{url}/batch", json={"orders": make_orders(s)})
    return resp.json()["results"][s.symbol]


@app.post("/order/simulation")
async def simulation(stocks: list[StockConfig]):
    start = time.perf_counter()
    results = await asyncio.gather(*(run_batch(s) for s in stocks))
    return {
        "executionTimeMs": round((time.perf_counter() - start) * 1000, 2),
        "results": dict(zip((s.symbol for s in stocks), results)),
    }

HOW IT MAPS TO THE GO CODE
  asyncio.gather(...)            goroutines + sync.WaitGroup
  engines: dict[str, Task]       manager.go's map + mutex
  create_subprocess_exec         exec.Command(...).Start()
  lifespan's kill loop           StopAllEngines on SIGTERM
  httpx.AsyncClient (shared)     balancer.go's tuned http.Transport

IT ALSO FIXES THE GO SERIALIZATION BUG FROM LESSON 11
  engine_url() stores a Task (a "future result") for each symbol the
  moment it starts spawning. A second request for the same symbol awaits
  the SAME task, and requests for other symbols spawn in parallel. No
  lock is held during the 5-second readiness wait. asyncio runs on one
  thread, so "check the dict, then set it" can't be interrupted, as long
  as there's no await between the two.

5. OPTION C: PURE C++ (the hardest path, the most C++)
--------------------------------------------------------------------------------

Replace Go, and HTTP between the gateway and engines, with C++ talking a
BINARY protocol over TCP. This is how real trading systems work, and it
teaches memory layout, byte order, sockets, and async I/O.

A FIXED-SIZE MESSAGE (compiled and verified: sizeof == 24)
    struct NewOrderMsg {
        std::uint64_t id;          // offset 0
        std::int32_t  price;       // offset 8
        std::uint32_t quantity;    // offset 12
        std::uint8_t  side;        // offset 16
        std::uint8_t  orderType;   // offset 17
        std::uint8_t  padding[6];  // offsets 18-23: explicit padding
    };
    static_assert(sizeof(NewOrderMsg) == 24);
    static_assert(std::is_trivially_copyable_v<NewOrderMsg>);

  Why explicit padding? The compiler inserts invisible padding to align
  fields (the uint64_t forces 8-byte alignment of the whole struct).
  Making it explicit means both sides agree on every byte.
  static_assert checks it at COMPILE time.

  Reading bytes into a struct: use std::memcpy, not reinterpret_cast.
  Casting a raw byte buffer to NewOrderMsg* can break alignment and
  "strict aliasing" rules, which is undefined behavior.
      NewOrderMsg msg;
      std::memcpy(&msg, buffer, sizeof msg);

  Byte order: both ends on the same machine agree. Across different
  machines, pick a byte order (network order = big-endian) and convert.

THE SERVER LOOP (a sketch using standalone Asio, NOT compiled here, since
Asio isn't installed. Install it with: brew install asio)
    #include <asio.hpp>

    int main() {
        asio::io_context io;
        asio::ip::tcp::acceptor acceptor(io, {asio::ip::tcp::v4(), 7000});
        Orderbook book;
        for (;;) {
            asio::ip::tcp::socket socket = acceptor.accept();
            try {
                for (;;) {
                    NewOrderMsg msg;
                    asio::read(socket, asio::buffer(&msg, sizeof msg));  // exactly 24 bytes
                    auto trades = book.add({msg.id, static_cast<Side>(msg.side),
                                            static_cast<OrderType>(msg.orderType),
                                            msg.price, msg.quantity});
                    // write back a fixed-size TradeMsg for each trade ...
                }
            } catch (const asio::system_error&) {
                // client disconnected
            }
        }
    }

  From there: async_read/async_write, one engine thread per symbol with
  the BlockingQueue from lesson 11, and a gateway process that spawns the
  engines with posix_spawn (or Boost.Process).

6. OPTIONS D, E, F IN BRIEF
--------------------------------------------------------------------------------

D. TYPESCRIPT (Node + Hono). Sketch, not run here. Same shape as Option B:
    import { Hono } from "hono";
    import { serve } from "@hono/node-server";
    import { spawn } from "node:child_process";

    const ENGINE = process.env.ENGINE_PATH ?? "./engine_server";
    const engines = new Map<string, Promise<string>>();
    let nextPort = 6060;

    async function start(port: number): Promise<string> {
      spawn(ENGINE, [String(port)], { stdio: "ignore" });
      const url = `http://127.0.0.1:${port}`;
      for (let i = 0; i < 50; i++) {
        try { if ((await fetch(`${url}/status`)).ok) return url; } catch {}
        await new Promise((r) => setTimeout(r, 100));
      }
      throw new Error(`engine on ${port} never became ready`);
    }

    function engineUrl(symbol: string): Promise<string> {
      let p = engines.get(symbol);
      if (!p) { p = start(nextPort++); engines.set(symbol, p); }
      return p;
    }

    const app = new Hono();
    app.post("/order/batch/:symbol", async (c) => {
      const url = await engineUrl(c.req.param("symbol"));
      const r = await fetch(`${url}/batch`, {
        method: "POST",
        headers: { "content-type": "application/json" },
        body: JSON.stringify(await c.req.json()),
      });
      return c.json(await r.json());
    });
    serve({ fetch: app.fetch, port: 8000 });

  Upside: your frontend is already TypeScript, so there's one language
  for the whole web side. Downside: it teaches you nothing about C++.

E. RUST (axum + tokio): the fastest and safest gateway option, and Rust's
  ownership rules formalize what lessons 04-08 teach. But learning Rust
  and C++ at the same time is a lot. Come back to it after you're
  comfortable in C++, and try rewriting the order book in Rust. It's a
  fantastic comparison exercise.

F. ELIXIR (Phoenix + OTP): each engine becomes a supervised external
  process (a Port). If it crashes, the supervisor restarts it
  automatically. That's the part manager.go only half does (it detects
  unhealthy engines but never restarts them).

7. RECOMMENDATION
--------------------------------------------------------------------------------

  Want the most C++ learning for the least side-quest?  -> Option A
  Want to keep the "one process per stock" architecture? -> Option B,
                                                            then C later
  Want to go deep on systems programming?                -> Option C
  Want one language across the frontend + gateway?       -> Option D

  Suggested path: A first (milestones 1-4 in lesson 16). Then, as a stretch,
  replace HTTP with Option C's binary protocol.
