  LESSON 03 — CLASSES, CONSTRUCTORS, AND const
  Part 1: Foundations  |  ~1.5 hrs  |  Prereqs: 02

GOAL
----
- Write classes with enforced public/private access.
- Use constructor member initializer lists (and know the ordering trap).
- Mark methods const, and understand why the compiler enforces it.
- Know when to use struct vs class.
- Understand that objects live on the stack by default (no "new" needed).


PYTHON VS C++
-------------
Python: a class is a dict of attributes you can add to at any time.
"Private" is a naming convention (_name). self is passed explicitly.
Every object lives on the heap and is garbage collected.

C++: a class has a FIXED layout decided at compile time. You can't add
fields at runtime. public/private is enforced by the compiler. "this" is
implicit. Objects can live directly on the stack or inside other objects,
and they're destroyed at a precise, predictable moment.


--------------------------------------------------------------------------------
1. ANATOMY OF A CLASS
--------------------------------------------------------------------------------

    class Order {
    public:                                     // accessible from anywhere
        Order(OrderId id, Price price, Quantity qty)   // constructor
            : id_(id), price_(price), remaining_(qty) {}   // initializer list

        OrderId  GetId() const { return id_; }            // const method
        Quantity GetRemaining() const { return remaining_; }

        void Fill(Quantity q) { remaining_ -= q; }        // non-const: modifies

    private:                                    // only this class can touch
        OrderId  id_;
        Price    price_;
        Quantity remaining_;
    };                                          // <- the semicolon is REQUIRED

    Order o(1, 100, 10);          // creates an Order ON THE STACK. No "new".
    o.Fill(3);
    o.remaining_ = 0;             // COMPILE ERROR: remaining_ is private

Python equivalent:
    class Order:
        def __init__(self, id, price, qty):
            self._id = id; self._price = price; self._remaining = qty

Naming convention: this repo (and much of the industry) uses a trailing
underscore for member variables (id_), so you can tell members apart from
parameters. Some codebases use m_id instead.


--------------------------------------------------------------------------------
2. MEMBER INITIALIZER LISTS
--------------------------------------------------------------------------------

    Order(OrderId id, Price price, Quantity qty)
        : id_(id), price_(price), remaining_(qty) {}

The part after the colon INITIALIZES members directly. The alternative,
assigning inside the body, first default-constructs each member and then
overwrites it:

    Order(OrderId id, Price price, Quantity qty) {
        id_ = id; price_ = price; remaining_ = qty;   // works, but worse
    }

Use initializer lists because:
  - const members and reference members CAN'T be assigned; they MUST be
    initialized.
  - Members without a default constructor must be initialized.
  - It avoids the wasted default-construct-then-assign step.

THE ORDERING TRAP
  Members are ALWAYS initialized in the order they're DECLARED in the
  class, NOT the order you write them in the initializer list.

    class Bad {
        int a_;
        int b_;
    public:
        Bad(int x) : b_(x), a_(b_ * 2) {}   // a_ is initialized FIRST,
    };                                       // reading b_ before it's set!

  The compiler warns about this (-Wreorder). When the course was written,
  it flagged exactly this in the repo:

      Server.cpp:55:9: warning: field 'asks_' will be initialized after
                       field 'bids_' [-Wreorder-ctor]

  It's harmless there because neither member depends on the other, but
  it's a habit to fix. Always write initializer lists in declaration
  order.


--------------------------------------------------------------------------------
3. const METHODS AND const CORRECTNESS
--------------------------------------------------------------------------------

    Quantity GetRemaining() const { return remaining_; }
                            ^^^^^
"This method promises not to modify the object." The compiler enforces
it: assigning to a member inside a const method is a compile error.

Why it matters: when you have a const object or a const reference (lesson
04), you can ONLY call its const methods.

    void print(const Order& o) {
        o.GetRemaining();   // OK: const method
        o.Fill(1);          // COMPILE ERROR: Fill isn't const
    }

This is "const correctness": mark everything const that can be const. It
documents intent and lets the compiler catch accidental mutation. Python
has nothing like it.

Other uses of const:
    const int maxOrders = 1000;          // can't be changed
    const std::string& name              // read-only reference (lesson 04)


--------------------------------------------------------------------------------
4. struct VS class
--------------------------------------------------------------------------------

The ONLY technical difference: struct members default to public, class
members default to private.

Convention:
  struct -> plain bundle of data, no invariants to protect
            (like a Python @dataclass)
  class  -> has invariants to protect, so data is private and access goes
            through methods

    struct LevelInfo { Price price_; Quantity quantity_; };
    LevelInfo li{100, 50};      // "aggregate initialization" with braces


--------------------------------------------------------------------------------
5. BRACE INITIALIZATION
--------------------------------------------------------------------------------

    int a{5};
    std::vector<int> v{1, 2, 3};
    LevelInfo li{100, 50};
    Trade t{TradeInfo{1, 100, 5}, TradeInfo{2, 100, 5}};

Braces also prevent "narrowing" conversions:
    int x = 3.7;      // compiles, silently becomes 3
    int y{3.7};       // COMPILE ERROR: narrowing

  One gotcha: std::vector<int> v(3, 0) is three zeros, but
  std::vector<int> v{3, 0} is the two elements 3 and 0.


--------------------------------------------------------------------------------
6. DESTRUCTORS (preview of lessons 05 and 10)
--------------------------------------------------------------------------------

    class Logger {
    public:
        Logger()  { std::cout << "created\n"; }
        ~Logger() { std::cout << "destroyed\n"; }    // destructor
    };

    void f() {
        Logger l;          // prints "created"
        // ...
    }                      // l goes out of scope: prints "destroyed". ALWAYS.

In Python, __del__ runs "whenever the garbage collector gets around to
it". In C++ the destructor runs at a precise moment: when the object's
scope ends. This single fact powers RAII (lesson 10).

PITFALLS
--------
- Forgetting the ; after a class's closing brace (confusing error message).
- Initializer list order not matching declaration order.
- Forgetting const on getters, then being unable to call them through a
  const reference.
- Writing "Order o = new Order(...)". That's Java/C#. In C++, "new"
  returns a pointer and you almost never want it (lesson 05).
- Leaving members uninitialized: "int x_;" with no initializer holds
  GARBAGE, not 0. Give default values: "int x_ = 0;" or "int x_{};"


EXERCISES
---------
1. Write class BankAccount with a private balance_ (std::int64_t cents),
   a constructor, a const Balance() method, and Deposit/Withdraw methods.
   Withdraw should throw std::runtime_error on insufficient funds.

2. Make a function void show(const BankAccount& a) that calls Balance().
   Then remove const from Balance() and read the compiler error.

3. Reproduce the ordering trap: a class with members a_ then b_, where the
   initializer list sets b_ first and computes a_ from b_. Compile with
   -Wall and see the warning. Print a_ and see the garbage.

4. Add a destructor to BankAccount that prints a message. Create accounts
   in nested { } blocks and watch the order they're destroyed in (the
   reverse of the order they were created).

5. Fix the reorder warning in Server.cpp:53-56 in your head: which line
   moves where?
