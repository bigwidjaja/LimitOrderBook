PYTHON VS C++
-------------
Python: the GIL (Global Interpreter Lock) means only one thread runs Python
code at a time, so threads mostly help with waiting on I/O. Many simple
races are hidden by the GIL.

C++: no GIL. Threads run truly in parallel on all your cores. That's real
speed, and real danger: two threads touching the same data without
synchronization is a DATA RACE, and a data race is undefined behavior.


--------------------------------------------------------------------------------
1. THREADS  (#include <thread>)
--------------------------------------------------------------------------------

    std::thread t([] { std::cout << "hello from a thread\n"; });
    t.join();    // wait for it to finish

You MUST join() (wait for it) or detach() (let it run on its own) every
std::thread before it's destroyed. Otherwise the program terminates.

C++20 std::jthread joins automatically in its destructor (RAII again). It
needs a recent standard library, so check that your compiler supports it.

    std::vector<std::thread> workers;
    for (int i = 0; i < 4; ++i)
        workers.emplace_back([i] { work(i); });   // capture i BY VALUE
    for (auto& w : workers) w.join();

Go comparison: "go f()" + sync.WaitGroup  ~  std::thread + join().


--------------------------------------------------------------------------------
2. DATA RACES ARE REAL (and UB makes them sneaky)
--------------------------------------------------------------------------------

Four threads each increment a shared long 100,000 times with ++racy and no
lock. Actual results when this course was written:

    built with -O0:   115961, 138592, 110856    (expected 400000)
    built with -O2:   400000

The -O0 build loses most of the increments, because "++racy" is really
read, add, write, and threads overwrite each other's writes.

The -O2 build printing the right answer is WORSE, not better. Because a
data race is UB, the optimizer is allowed to assume no other thread
touches racy, so it merged the loop into one big addition. The bug is
still there. It'll show up the day the code gets a little more
complicated. This is why you can't test your way out of races. Use
ThreadSanitizer:

    clang++ -std=c++20 -g -fsanitize=thread race.cpp -o race && ./race


--------------------------------------------------------------------------------
3. MUTEXES AND LOCKS  (#include <mutex>)
--------------------------------------------------------------------------------

    std::mutex mu;
    long total = 0;

    void add() {
        std::lock_guard<std::mutex> lock(mu);   // locks now
        ++total;
    }                                           // unlocks here (RAII)

  Never call mu.lock() and mu.unlock() by hand. If anything between them
  throws or returns, the mutex stays locked forever.

  std::lock_guard    simplest: lock for the whole scope
  std::scoped_lock   like lock_guard, but can lock SEVERAL mutexes at once
                     without deadlock:  std::scoped_lock lk(m1, m2);
  std::unique_lock   can unlock and relock early; needed for condition
                     variables
  std::shared_mutex  many readers OR one writer (like Go's sync.RWMutex)

DEADLOCK: thread A holds m1 and waits for m2 while thread B holds m2 and
waits for m1. Avoid it by always locking in the same order, or by using
scoped_lock for multiple mutexes.

KEEP CRITICAL SECTIONS SMALL: do the slow work (I/O, formatting, logging)
outside the lock.


--------------------------------------------------------------------------------
4. ATOMICS  (#include <atomic>)
--------------------------------------------------------------------------------

For a single counter or flag, a mutex is overkill:

    std::atomic<long> hits{0};
    hits.fetch_add(1);     // or ++hits; thread-safe, no lock
    hits.load();

  (Four threads x 100,000 fetch_adds gave exactly 400000 at every
  optimization level.)

Atomics only make ONE operation indivisible. "if (x == 0) x = 1;" on an
atomic is still two operations, which is a race. Use compare_exchange or a
mutex for multi-step logic.


--------------------------------------------------------------------------------
5. CONDITION VARIABLES: A THREAD-SAFE QUEUE
--------------------------------------------------------------------------------

The standard way to hand work from one thread to another. It's the C++
equivalent of a Go channel or Python's queue.Queue. (This code was
compiled and tested: 4 producer threads x 1000 orders -> 4000 processed.)

    template <typename T>
    class BlockingQueue {
    public:
        void push(T item) {
            {
                std::lock_guard<std::mutex> lock(mu_);
                items_.push_back(std::move(item));
            }
            cv_.notify_one();                 // wake one waiting consumer
        }

        std::optional<T> pop() {              // nullopt = queue closed and empty
            std::unique_lock<std::mutex> lock(mu_);
            cv_.wait(lock, [this] { return !items_.empty() || closed_; });
            if (items_.empty()) return std::nullopt;
            T item = std::move(items_.front());
            items_.pop_front();
            return item;
        }

        void close() {
            {
                std::lock_guard<std::mutex> lock(mu_);
                closed_ = true;
            }
            cv_.notify_all();
        }

    private:
        std::mutex mu_;
        std::condition_variable cv_;
        std::deque<T> items_;
        bool closed_ = false;
    };

    // one engine thread owns the order book; everyone else just pushes
    BlockingQueue<NewOrder> queue;
    std::thread engine([&] {
        while (auto order = queue.pop()) { book.add(*order); }
    });

cv_.wait(lock, predicate) sleeps until notified AND the predicate is true.
It re-checks the predicate because of "spurious wakeups".


--------------------------------------------------------------------------------
6. DESIGN: ONE BIG LOCK VS ONE THREAD PER BOOK
--------------------------------------------------------------------------------

DESIGN A (this repo): many threads, one global mutex around everything.
  Simple and correct, but every request waits for every other request,
  even requests for unrelated books.

DESIGN B (real exchanges): each order book is owned by exactly ONE thread.
  Other threads only push messages onto that thread's queue. The book
  itself needs no locks at all, because only one thread ever touches it.
  This is the "single-writer principle" (the LMAX Disruptor architecture
  is the famous example). Different symbols run on different threads, in
  parallel.

This repo gets parallelism a third way: ONE PROCESS per symbol (lesson 13).
That works, but the processes talk over HTTP, which costs far more time
than the matching itself.

PITFALLS
--------
- Forgetting to join a std::thread (the program terminates).
- Capturing loop variables by reference in thread lambdas.
- Believing a race is fixed because the output looks right (section 2).
- Holding locks during I/O or slow calls.
- Locking two mutexes in different orders in different places.
- Returning a reference to data protected by a mutex; the caller then uses
  it without the lock.
