GOAL
----
- Think in terms of OWNERSHIP: who is responsible for destroying an object?
- Use std::unique_ptr (one owner) and std::shared_ptr (shared owners).
- Understand move semantics and std::move.
- Know the "rule of zero".
- Judge whether this repo's use of shared_ptr is the best design.


PYTHON VS C++
-------------
Python: a garbage collector tracks references and frees objects "at some
point" after nothing refers to them. You never think about it.

C++: there is no garbage collector. Every heap object has an OWNER, and the
owner destroys it at a precise moment. Get it right and you get
deterministic, fast cleanup. Get it wrong and you get leaks (never freed)
or use-after-free (freed too early, lesson 08). Smart pointers make getting
it right the easy default.


--------------------------------------------------------------------------------
1. THE OLD WAY (so you recognize it and never write it)
--------------------------------------------------------------------------------

    Order* o = new Order(1, 100, 10);   // allocate on the heap
    // ... if anything here throws or returns early ...
    delete o;                           // ... this never runs: LEAK

Raw new/delete is error-prone: leaks, double deletes, deleting too early.
Modern C++ rule: DON'T WRITE new OR delete IN APPLICATION CODE.


--------------------------------------------------------------------------------
2. std::unique_ptr — EXACTLY ONE OWNER  (#include <memory>)
--------------------------------------------------------------------------------

    auto o = std::make_unique<Order>(1, 100, 10);   // heap object, one owner
    o->GetId();
    // when o goes out of scope, the Order is deleted automatically

A unique_ptr CANNOT be copied (that would mean two owners). It can be
MOVED, which transfers ownership:

    auto p = std::make_unique<Order>(1, 100, 10);
    auto q = p;              // COMPILE ERROR: can't copy
    auto q = std::move(p);   // OK: q owns the Order now, p is nullptr

  (Verified: after the move, p == nullptr is true.)

Cost: zero. A unique_ptr is the same size as a raw pointer, and its
cleanup is just a delete at the right time.

unique_ptr is the DEFAULT choice for heap objects. Reach for shared_ptr
only when you truly need shared ownership.


--------------------------------------------------------------------------------
3. std::shared_ptr — SHARED OWNERSHIP (reference counted)
--------------------------------------------------------------------------------

    auto a = std::make_shared<Order>(1, 100, 10);   // count = 1
    auto b = a;                                     // count = 2 (copying OK)
    // the Order is deleted when the LAST shared_ptr to it is gone

    a.use_count();   // 2

This is the closest thing to Python's model, but explicit and opt-in.

Costs:
  - An extra heap-allocated "control block" holding the count
    (make_shared allocates it alongside the object, in one allocation).
  - Every copy and destruction updates the count ATOMICALLY (thread-safe),
    which is slower than a plain integer update.
  - Cycles leak: if A holds a shared_ptr to B and B holds one to A, neither
    count ever reaches 0. Break cycles with std::weak_ptr (a non-owning
    observer).

Use make_shared / make_unique rather than shared_ptr<T>(new T(...)).


--------------------------------------------------------------------------------
4. NON-OWNING ACCESS
--------------------------------------------------------------------------------

If a function just needs to USE an object, don't pass the smart pointer.
Pass a reference (or a raw pointer if it can be null):

    void print(const Order& o);            // good: works with any owner
    void print(std::shared_ptr<Order> o);  // meh: copies, bumps the count

"Smart pointer in a signature" should mean "this function takes part in
ownership", not "this function looks at the object".


--------------------------------------------------------------------------------
5. MOVE SEMANTICS
--------------------------------------------------------------------------------

Copying a vector of a million elements copies a million elements. But if
the source is about to be thrown away, we could just steal its internal
buffer. That's a MOVE.

    std::vector<int> make_big();
    std::vector<int> v = make_big();       // result is moved (or elided): cheap

    std::string a = "a long string ...";
    std::string b = std::move(a);          // b steals a's buffer
    // a is now "valid but unspecified", usually empty. Don't rely on its
    // value; you can only assign to it or destroy it.

std::move doesn't move anything by itself. It's a cast that says "I'm done
with this, you may steal from it." The move happens in the move
constructor of the receiving object.

Common uses:
    orders.push_back(std::move(order));    // hand an object to a container
    member_ = std::move(param);            // "sink" parameter into a member

EMPLACE: build the element in place, with no temporary at all:
    std::vector<Order> v;
    v.emplace_back(1, 100, 10);            // calls Order's constructor inside v

(You'll hear about "lvalues" and "rvalues", and "T&&" rvalue references.
Short version: T&& binds to temporaries or std::move'd things, and that's
how move constructors are selected. You rarely write T&& yourself outside
of move constructors and templates.)


--------------------------------------------------------------------------------
6. THE RULE OF ZERO (and three/five)
--------------------------------------------------------------------------------

A class can define five special members: destructor, copy constructor,
copy assignment, move constructor, move assignment.

RULE OF ZERO: if your members are all well-behaved types (int, string,
vector, unique_ptr, map...), write NONE of these. The compiler generates
correct ones. Every class in this repo follows the rule of zero, and so
should yours.

RULE OF FIVE: if you manage a raw resource yourself (a file handle, a
socket, raw memory) and write a destructor, you probably need to write or
delete all five. Better: wrap the resource in its own small class once,
then go back to the rule of zero everywhere else.

DESIGN CRITIQUE: is shared ownership really needed?
  The Orderbook is the only real owner of orders; nothing outside keeps
  them alive. A simpler, faster design is for the price-level list to own
  the Order BY VALUE and for the index to store only an iterator:

      std::map<Price, std::list<Order>, std::greater<Price>> bids_;
      std::unordered_map<OrderId, std::list<Order>::iterator> index_;

  That design has no shared_ptr, no per-order control block, and no atomic
  reference counting. Lesson 14 builds exactly this; it was compiled and
  tested while writing this course.

  Because the list owns each Order, erasing it from the list destroys it.
  So you must be careful about the ORDER of operations: read what you need
  (the id, the price) BEFORE erasing. That's the exact class of bug in
  lesson 08.


PITFALLS
--------
- Using an object after std::move-ing it.
- Using shared_ptr "just to be safe". It hides who really owns what.
- shared_ptr cycles (use weak_ptr for back-references).
- Passing smart pointers into functions that only need to read.
- "delete"-ing something owned by a smart pointer (double free).
- Calling .get() on a smart pointer and keeping the raw pointer after the
  owner is gone.
