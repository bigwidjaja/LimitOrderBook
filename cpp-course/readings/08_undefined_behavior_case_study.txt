- Use sanitizers so the tools catch these bugs for you.


PYTHON VS C++
-------------
Python: if you do something invalid, you get an exception with a traceback.
Always. The same code behaves the same way on every machine.

C++: some invalid operations are "undefined behavior". The language
standard makes NO promises about what happens. The program might:
  - appear to work perfectly (the most dangerous outcome)
  - crash immediately
  - crash later, somewhere unrelated
  - silently corrupt data
  - behave differently on Windows vs macOS, or at -O0 vs -O2
The compiler is allowed to assume UB never happens and optimize based on
that, which can make the results look impossible.


--------------------------------------------------------------------------------
1. THE COMMON KINDS OF UB
--------------------------------------------------------------------------------

  Use-after-free        using an object after it has been destroyed
  Dangling reference    a reference/pointer/iterator to a destroyed object
  Out-of-bounds access  v[10] on a 3-element vector
  Invalidated iterator  using an iterator after the container changed it
  Signed int overflow   INT32_MAX + 1
  Uninitialized read    reading "int x;" before assigning it
  Null dereference      *p when p == nullptr
  Data race             two threads touching the same data, at least one
                        writing, without synchronization (lesson 11)

The first four are all the same underlying problem: touching memory whose
owner has already destroyed it or never owned it.

2. CASE STUDY 1: THE BUG THAT WAS FIXED ("fixed order matching on macOS")
--------------------------------------------------------------------------------

Commit e107e23 changed MatchOrders. Here's the core of the OLD version:

    while (!bids.empty() && !asks.empty()) {
        auto& bid = bids.front();     // reference to the list's first element
        auto& ask = asks.front();
        Quantity quantity = std::min(bid->GetRemainingQuantity(),
                                     ask->GetRemainingQuantity());
        bid->Fill(quantity);
        ask->Fill(quantity);

        if (bid->IsFilled()) {
            bids.pop_front();                  // (1) destroys the element bid refers to
            orders_.erase(bid->GetOrderId());  // (2) uses bid: USE-AFTER-FREE
        }
        if (ask->IsFilled()) {
            asks.pop_front();
            orders_.erase(ask->GetOrderId());  // same bug
        }

        if (bids.empty()) { bids_.erase(bidPrice); }   // (3) destroys the whole list
        if (asks.empty()) { asks_.erase(askPrice); }   //     that "bids" refers to...

        trades.push_back(Trade{
            TradeInfo{ bid->GetOrderId(), ... },       // (4) uses bid again
            TradeInfo{ ask->GetOrderId(), ... } });
    }                                                  // (5) loop condition reads
                                                       //     the destroyed list

Why it "worked" on Windows and crashed on macOS: after pop_front, the
memory usually still holds the old bytes for a little while. Windows'
allocator happened to leave them intact long enough; macOS' allocator
reused or scrambled them sooner. Neither behavior is "correct". The code
was always broken.

THE FIX (current code, Server.cpp:248-289):
  - Record the trade BEFORE popping anything (lines 261-264).
  - Copy the id into a plain value BEFORE popping:
        OrderId bidId = bid->GetOrderId();   // a copy, not a reference
        bids.pop_front();
        orders_.erase(bidId);                // uses the copy: safe
  - Erase empty price levels AFTER the inner loop finishes (lines 282-289).

THE LESSON: after you destroy something, nothing that referred to it may
be used. Copy out what you need FIRST.

3. CASE STUDY 2: THE BUG THAT'S STILL THERE (CancelOrder)
--------------------------------------------------------------------------------

    void CancelOrder(OrderId orderId) {
        if (!orders_.contains(orderId)) return;

        const auto& [order, orderIterator] = orders_.at(orderId);   // line 367
        orders_.erase(orderId);                                     // line 368

        if (order->GetSide() == Side::Sell) {        // uses order: UB
            auto price = order->GetPrice();          // UB
            auto& orders = asks_.at(price);
            orders.erase(orderIterator);             // uses orderIterator: UB
            ...

What's wrong: "const auto& [order, orderIterator]" binds REFERENCES to the
two members of the OrderEntry stored inside the unordered_map. Line 368
erases that map entry, which destroys the OrderEntry. "order" and
"orderIterator" now refer to freed memory, and every line after that
reads it.

(The Order object itself is still alive, because the price-level list
holds another shared_ptr to it. What's destroyed is the map's copy of the
shared_ptr and the iterator, which is exactly what we then read.)

HOW IT WAS CONFIRMED while writing this course
  A small test program added one order and cancelled it.
    - Normal run:          exits 0, looks fine
    - MallocScribble=1:    segmentation fault (exit code 139)
  MallocScribble is a macOS allocator setting that overwrites freed memory
  with garbage. The code was reading freed memory the whole time; it just
  happened to still contain the old bytes.

THE FIX: copy the entry instead of referencing it (drop the &):

        auto [order, orderIterator] = orders_.at(orderId);   // copies
        orders_.erase(orderId);                              // safe now

  Copying a shared_ptr and an iterator is cheap. With that one-character
  change, the same test passes even with MallocScribble=1 (also verified).

SAME BUG, SECOND PLACE: the modify function (Server.cpp:389-398, misnamed
MatchOrder):

        const auto& [existingOrder, _] = orders_.at(order.GetOrderId());
        CancelOrder(order.GetOrderId());                     // erases that entry
        return AddOrder(order.ToOrderPointer(existingOrder->GetOrderType()));
                                             // ^ uses the destroyed entry: UB

  Fix: copy what you need before cancelling.
        OrderType type = orders_.at(order.GetOrderId()).order_->GetOrderType();
        CancelOrder(order.GetOrderId());
        return AddOrder(order.ToOrderPointer(type));


--------------------------------------------------------------------------------
4. TOOLS THAT CATCH UB FOR YOU
--------------------------------------------------------------------------------

ADDRESSSANITIZER (ASan): detects use-after-free, out-of-bounds access, and
leaks, and prints exactly where the memory was allocated, freed, and then
misused.
    clang++ -std=c++20 -g -O1 -fsanitize=address -fno-omit-frame-pointer x.cpp -o x
    ./x

UNDEFINEDBEHAVIORSANITIZER (UBSan): signed overflow, null dereference,
misaligned access, and more.
    -fsanitize=undefined          (combine: -fsanitize=address,undefined)

THREADSANITIZER (TSan): data races (lesson 11). Can't be combined with ASan.
    -fsanitize=thread

MALLOCSCRIBBLE (macOS only, no rebuild needed):
    MallocScribble=1 ./x

COMPILER WARNINGS: -Wall -Wextra catch the simple cases (like returning a
reference to a local).

YOUR RULE FROM NOW ON: every debug build and every test run uses
-fsanitize=address,undefined. It makes the program 2-3x slower, and it
turns silent bugs into loud ones.


--------------------------------------------------------------------------------
5. HOW TO TEST ONE CLASS FROM A FILE THAT HAS ITS OWN main()
--------------------------------------------------------------------------------

Server.cpp has its own main(), and the Orderbook class isn't in a
separate header, so you can't just #include it into a test. A quick hack
(which is exactly how the bug above was reproduced):

    // cancel_test.cpp, placed next to Server.cpp
    #define main server_main       // rename Server.cpp's main
    #include "Server.cpp"
    #undef main

    int main() {
        Orderbook book;
        book.AddOrder(std::make_shared<Order>(
            OrderType::GoodTillCancel, Side::Buy, 100, 10, 1));
        book.CancelOrder(1);
        std::cout << "\nsize after cancel: " << book.Size() << "\n";
    }

    clang++ -std=c++20 -g -fsanitize=address -I. cancel_test.cpp -o cancel_test
    ./cancel_test

This hack is a sign the code should be split into headers and source
files, so tests can include the order book alone. Lesson 14 does that.


PITFALLS
--------
- "It works on my machine" means nothing when UB is involved.
- Believing "it passed the tests" proves there's no UB. It doesn't, unless
  the tests run under sanitizers.
- References from structured bindings (auto& [a, b] = ...) look like
  local variables but aren't; they refer into the container.
- Adding debug prints and seeing the bug disappear. With UB, that's
  common, and it doesn't mean the bug is fixed.
