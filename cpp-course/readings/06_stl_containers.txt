GOAL
----
- Know the main standard containers and their Python equivalents.
- Pick a container based on Big-O costs AND memory layout.
- Use custom comparators (a template argument that changes behavior).
- Avoid the operator[] insertion trap.
- Understand WHY the order book uses the containers it does.


PYTHON VS C++
-------------
Python gives you list, dict, set, tuple, collections.deque, and heapq, and
mostly hides how they work.

C++ gives you a dozen containers, each with different costs, and expects
you to choose. The order book is essentially a lesson in picking the right
container for each job.


--------------------------------------------------------------------------------
1. THE MAIN CONTAINERS
--------------------------------------------------------------------------------

  C++                         Python-ish equivalent     What it is
  --------------------------  ------------------------  ---------------------
  std::vector<T>              list                      dynamic array
  std::array<T, N>            (fixed-size tuple)        fixed-size array
  std::deque<T>               collections.deque         double-ended queue
  std::list<T>                (none)                    doubly linked list
  std::map<K, V>              dict kept SORTED by key   balanced tree
  std::unordered_map<K, V>    dict                      hash table
  std::set / unordered_set    sorted set / set          same, keys only
  std::pair / std::tuple      tuple                     fixed bundle
  std::priority_queue<T>      heapq                     heap

Every container holds ONE element type. No mixing ints and strings.


--------------------------------------------------------------------------------
2. COSTS (n = number of elements)
--------------------------------------------------------------------------------

  vector:        index O(1), push_back O(1) amortized, insert/erase in the
                 middle O(n). Contiguous memory = the fastest to iterate
                 (CPU caches love it).
  list:          insert/erase anywhere O(1) IF you have an iterator. No
                 indexing; finding something is O(n). Each element is a
                 separate heap allocation (slow to iterate).
  map:           find/insert/erase O(log n). Always sorted. begin() is the
                 smallest key (by the comparator).
  unordered_map: find/insert/erase O(1) average. No ordering.
  deque:         O(1) push/pop at both ends.

Real-world rule: std::vector is the default. It's often faster than
"better Big-O" containers for small n because of memory locality. Choose
something else when you have a concrete reason.


--------------------------------------------------------------------------------
3. vector ESSENTIALS
--------------------------------------------------------------------------------

    std::vector<int> v;
    v.reserve(1000);        // allocate room for 1000 up front (size is still 0)
    v.push_back(5);
    v.emplace_back(6);      // construct in place
    v.size();               // number of elements
    v.capacity();           // allocated room
    v[0];                   // no bounds check: out of range is UNDEFINED BEHAVIOR
    v.at(0);                // bounds-checked: throws std::out_of_range
    v.back(); v.front();
    v.pop_back();
    v.clear();

When size reaches capacity, push_back allocates a bigger buffer and moves
everything over. reserve() avoids repeated reallocation when you know
roughly how many elements are coming.


--------------------------------------------------------------------------------
4. map AND unordered_map ESSENTIALS
--------------------------------------------------------------------------------

    std::map<std::string, int> m;
    m["AAPL"] = 100;              // insert or overwrite
    m.insert({"GOOG", 200});      // insert only if the key is absent
    m.contains("AAPL");           // C++20. Before that: m.count(k) or m.find(k)
    m.at("AAPL");                 // throws std::out_of_range if missing
    auto it = m.find("MSFT");     // returns m.end() if missing
    if (it != m.end()) { it->first; it->second; }
    m.erase("AAPL");

    for (const auto& [key, value] : m) { ... }   // sorted order for std::map

THE operator[] TRAP  (Python developers hit this constantly)
    int x = m["missing"];   // DOES NOT throw. It INSERTS "missing" -> 0.
  Python's d["missing"] raises KeyError. C++'s m["missing"] silently
  creates a default entry. Use .find(), .contains(), or .at() when you
  only want to look something up.

  (Verified while writing: after reading m["missing"], m.size() == 1.)


--------------------------------------------------------------------------------
5. CUSTOM COMPARATORS (a first taste of templates)
--------------------------------------------------------------------------------

std::map sorts keys with std::less<K> (ascending) by default. You can
change that with a template argument:

    std::map<int, std::string, std::greater<int>> bids;   // descending
    bids[100] = "a"; bids[105] = "b"; bids[99] = "c";
    bids.begin()->first;    // 105: the HIGHEST price comes first

This is how the order book gets the best bid in O(1): bids are sorted
high-to-low, asks low-to-high, so begin() of each is the best price.

The comparator is part of the TYPE: map<int, X, greater<int>> and
map<int, X> are different types. Templates generate a separate class for
each combination at compile time, with zero runtime cost.


--------------------------------------------------------------------------------
6. HOW THE ORDER BOOK USES CONTAINERS
--------------------------------------------------------------------------------

  Need                                         Container chosen
  -------------------------------------------  ----------------------------
  Best bid instantly; walk prices high->low    map<Price, ..., greater>
  Best ask instantly; walk prices low->high    map<Price, ..., less>
  First-come-first-served within one price     list<OrderPointer> (FIFO)
  Find an order by id for cancel               unordered_map<OrderId, ...>
  Remove an order from the MIDDLE of a list    store the list iterator,
    in O(1)                                    so list::erase(it) is O(1)

  Resulting costs (L = number of price levels, which is usually small):
    add order (no match)  O(log L)   map lookup/insert, then list push_back
    cancel                O(log L)   hash lookup O(1), map lookup, list erase O(1)
    best bid/ask          O(1)       begin()
    each fill in a match  O(1)       plus O(log L) when a level empties

Why a list and not a deque or vector for each price level? You need O(1)
removal from the MIDDLE (cancellations), and you need stored iterators to
stay valid while other orders come and go. Only std::list guarantees both.
Lesson 07 explains the "stay valid" part.

      Orderbook& book = MyMap[s_book];
  Cancelling an order in a book that doesn't exist, e.g. book=ZZZZ,
  CREATES an empty ZZZZ order book, which then shows up in /status
  forever. It should use MyMap.find(s_book) and return 404 if not found.

  A HIDDEN PERFORMANCE COST (Server.cpp:225)
      trades.reserve(orders_.size());
  MatchOrders runs after EVERY AddOrder. With 10,000 resting orders,
  every single new order allocates room for 10,000 trades, even though
  most orders produce zero or one trade. reserve() is a good tool, but
  pick the number from what you actually expect.


PITFALLS
--------
- m[key] for lookups (silently inserts).
- v[i] out of bounds is undefined behavior, not an exception. Use .at()
  while learning, or build with sanitizers (lesson 08).
- Choosing std::list "for performance". It's usually SLOWER than vector,
  unless you need stable iterators or O(1) middle erasure.
- Iterating an unordered_map and expecting a consistent order.
- Modifying a container while looping over it (lesson 07).
