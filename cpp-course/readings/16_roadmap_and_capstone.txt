MILESTONE 3 — BENCHMARK AND OPTIMIZE
================================================================================

Measure first. A tested, no-library harness (the lesson 14b book does ~8
million orders/sec at -O2 on this Mac):

    #include "orderbook/orderbook.hpp"
    #include <chrono>
    #include <iostream>
    #include <random>

    int main() {
        std::mt19937 rng(42);
        std::uniform_int_distribution<int> price(90, 110), qty(1, 100), side(0, 1);
        constexpr int N = 2'000'000;
        std::vector<Order> orders;
        orders.reserve(N);
        for (int i = 0; i < N; ++i)
            orders.push_back({static_cast<OrderId>(i + 1),
                              side(rng) ? Side::Buy : Side::Sell,
                              OrderType::GoodTillCancel, price(rng),
                              static_cast<Quantity>(qty(rng))});

        Orderbook book;
        std::size_t trades = 0;
        auto start = std::chrono::steady_clock::now();
        for (const auto& o : orders) trades += book.add(o).size();
        auto secs = std::chrono::duration<double>(
            std::chrono::steady_clock::now() - start).count();
        std::cout << N << " orders, " << trades << " trades, "
                  << static_cast<long>(N / secs) << " orders/sec\n";
    }

  Build it in RELEASE mode (-O2, no sanitizers). Sanitizer builds are
  2-3x slower and not representative.

  Note that the orders are generated BEFORE the timer starts, so the timing
  measures only the order book.

Then use Google Benchmark for repeatable, statistically sound numbers.
(Standard usage, not compiled here because the library isn't installed.)

    # CMakeLists.txt
    set(BENCHMARK_ENABLE_TESTING OFF CACHE BOOL "" FORCE)
    FetchContent_Declare(benchmark
      GIT_REPOSITORY https://github.com/google/benchmark.git
      GIT_TAG        v1.9.0)
    FetchContent_MakeAvailable(benchmark)
    add_executable(orderbook_bench bench/orderbook_bench.cpp)
    target_link_libraries(orderbook_bench PRIVATE orderbook_core benchmark::benchmark_main)

    // bench/orderbook_bench.cpp
    #include <benchmark/benchmark.h>
    #include "orderbook/orderbook.hpp"

    static void BM_RestingOrders(benchmark::State& state) {
        Orderbook book;
        OrderId id = 0;
        for (auto _ : state) {
            auto trades = book.add({++id, Side::Buy, OrderType::GoodTillCancel,
                                    static_cast<Price>(id % 100), 10});
            benchmark::DoNotOptimize(trades);
        }
        state.SetItemsProcessed(state.iterations());
    }
    BENCHMARK(BM_RestingOrders);

  DoNotOptimize stops the compiler from deleting work whose result is
  unused (it's allowed to, and it will).

Optimization ideas, in the order you should try them:
  1. Run a profiler first to find where time goes. On macOS: Instruments
     (Time Profiler), or "xcrun xctrace". Don't guess.
  2. Avoid allocating a std::vector<Trade> for every add. Pass in a
     reusable output vector, or use a callback.
  3. Reserve the index_ hash map up front (index_.reserve(n)).
  4. Replace std::list's one-allocation-per-order with a pool or free list.
  5. If prices live in a small, known range: replace std::map with a
     vector indexed by price tick, plus a tracked best price.

Done when:
  [ ] You have a before/after table in your README for each optimization
  [ ] Every optimization kept all tests green
  [ ] You can explain why each one helped (or didn't)

================================================================================
NOT INTO ORDER BOOKS? SAME SKILLS, DIFFERENT PROJECT
================================================================================

Each of these exercises the same C++ concepts (containers, ownership,
iterators, concurrency, a clean core library + thin I/O layer):

  Redis-lite key-value server
      unordered_map + TTL expiry (a priority_queue), a TCP text protocol,
      snapshot to disk. Concepts: containers, sockets, RAII file handles.

  LRU cache library + Python binding
      list + unordered_map<Key, list::iterator>: the SAME iterator trick as
      the order book's cancel. Concepts: iterator stability, templates
      (make it LRUCache<K, V>).

  Rate limiter service (token bucket per client)
      Concepts: std::chrono, atomics, a sharded map with one mutex per shard.

  Tiny ray tracer
      Concepts: value types, operator overloading, performance, threads
      (render rows in parallel). Visual results are motivating.

  Log-file analyzer
      Concepts: std::string_view, parsing, memory-mapped files, parallel
      algorithms (std::execution::par, if your standard library supports it).
