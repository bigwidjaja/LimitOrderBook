WHO THIS IS FOR
---------------
You want a portfolio project that maps onto SIG's Market Data Libraries &
Tools team, and onto the intern description: "C++ CLI utilities alongside
low-level market data parsers for data ingestion from different exchange
feeds."

This is a DESIGN, not a tutorial. Lessons 01-12 teach the C++. Lesson 14
teaches the CMake/test layout. This file tells you WHAT to build, WHY
each piece exists, and which tech to use. Build it in a NEW repo, not
inside TradingEngine.

One sentence: a C++20 library that decodes two real exchange feeds and
rebuilds their books, plus CLI tools and Python bindings, built and tested
on Linux and Windows.

RULE: the libraries do not print, do not parse argv, and do not know
about Python. Tools and bindings call into them. Same rule as lesson 14.

WHY TWO FEEDS
  Nasdaq ITCH 5.0   market-by-order, big-endian, length-prefixed stream
  IEX DEEP          market-by-price, little-endian, inside IEX-TP inside
                    UDP inside a pcap

  Different byte order, different container, different book model. That
  forces a NORMALIZATION layer (one internal event type both feeds
  convert into). "Different exchange feeds" is the intern quote; two
  real specs is the smallest honest version of that.

5. CORE LIBRARY DESIGN
--------------------------------------------------------------------------------

5.1 ENDIAN HELPERS  (include/mdkit/endian.hpp)

  ITCH is big-endian. IEX DEEP is little-endian. x86 and Apple Silicon
  are little-endian. Never reinterpret_cast a multi-byte integer out of
  a buffer (alignment + aliasing = UB). Always copy bytes.

  The helper used in the prototype:

      template <typename T>
      T load_be(const std::byte* p) {
          T value = 0;
          for (std::size_t i = 0; i < sizeof(T); ++i)
              value = static_cast<T>(
                  (value << 8) | std::to_integer<std::uint8_t>(p[i]));
          return value;
      }

  Compiled with -O2 on this Mac, that loop became a single `rev`
  instruction (ARM byte-swap). Write it as a loop, let the compiler
  turn it into the CPU instruction. Same idea for load_le (no-op on
  little-endian hosts after optimization).

  ITCH timestamps are 6 bytes (nanoseconds since midnight). Need a
  dedicated load_be48.

  Prices are integers with 4 implied decimals (ITCH Price4). Never
  convert to double inside the library. Formatting for humans happens
  in the CLI: print 1600060 as "160.0060", zero-padded. A naive
  `price/10000` + `price%10000` printed "160.60" in an earlier test —
  that is a golden-file test waiting to happen.


5.2 DECODE STYLE: VISITOR, NOT A VARIANT PER MESSAGE

  Two ways to decode a stream:

    A. decode -> std::variant -> visit     (one heap-free object per msg)
    B. decode -> h.on(TypedMessage)        (the handler is a template)

  Use B on the hot path. The compiler monomorphizes the handler. A
  counting tool and a book builder become two different instantiations,
  and neither pays for a variant or virtual call.

  Handler concept (the prototype compiled with this):

      template <typename H>
      concept Handler = requires(H h, const AddOrder& a, DecodeError e) {
          h.on(a);
          h.on_error(e, 'A');
      };

  Default base so tools only override what they care about:

      struct IgnoreRest {
          template <typename M> void on(const M&) {}
          void on_error(DecodeError, char) {}
      };

      struct Counter : IgnoreRest {
          using IgnoreRest::on;          // keep the catch-all
          int adds = 0;
          void on(const AddOrder&) { ++adds; }
      };

  decode_message(span, handler) switches on the first byte (ITCH type
  char: 'A' add, 'E' execute, 'X' cancel, 'D' delete, 'U' replace, ...).
  It checks the spec length BEFORE reading fields. Wrong length is
  DecodeError::BadLength, not a crash.

  decode_stream(span, handler) walks length-prefixed frames:

      while remaining >= 2:
          len = load_be<uint16_t>(p)
          if remaining-2 < len: stop   // truncated tail is OK (partial file)
          decode_message(bytes[2 .. 2+len), handler)
          advance 2+len
      return bytes_consumed

  Verified on a hand-built stream: 3 adds + exec + cancel + replace +
  delete-unknown + unknown-type + truncated tail. Result: adds=3,
  errors=2, consumed=237/238 (the leftover byte is the truncated frame).


5.3 ITCH BOOK BUILDER

  ITCH is market-by-order. The feed identifies every order with a 64-bit
  Order Reference Number. You MUST keep a live-order index:

      unordered_map<OrderRef, Live> orders_;
      struct Live {
          uint16_t locate;   // ITCH's compact stock id (0..~10k)
          char     side;
          uint32_t price;
          uint32_t shares;
      };

  And one Book per locate. ITCH locate is a uint16, so a vector of 65536
  books is simpler and faster than a map:

      vector<Book> books_{65536};

  Book itself is the lesson-14 design: sorted maps of price ->
  {total shares, order count}. You do NOT need per-order lists at a
  price for most tools (mdbook prints aggregated depth). Keep the
  per-order data only in orders_.

  Apply rules (all verified in the prototype):

    Add     A   insert Live, book.add(side, price, shares)
    Exec    E   reduce shares; drop Live if remaining==0
    Cancel  X   same as Exec (partial cancel)
    Delete  D   reduce remaining shares, drop Live
    Replace U   delete oldRef, add newRef at new price/qty, SAME side
                (ITCH replace does not send side; you inherit it)

  Unknown refs increment a counter. Do not throw. Real days have
  oddities; a tool that dies on the first one is useless.

  Prototype run on a synthetic AAPL stream (locate 7):

      add  #1 BUY  100 @ 150.0000
      add  #2 BUY   50 @ 150.0000
      add  #3 SELL  30 @ 150.1000
      exec #1 40
      cancel #2 50          -> #2 gone, bid level now 60 x 1 order
      replace #3 -> #4 20 @ 150.2000
      delete #99            -> unknownRefs=1

      BID 1500000 shares=60 orders=1
      ASK 1502000 shares=20 orders=1
      live=2  unknownRefs=1


5.4 IEX PATH (second feed)

  IEX HIST files are gzip-compressed pcap/pcapng. Each packet is:

      Ethernet / IPv4 / UDP / IEX-TP header / one or more DEEP messages

  IEX-TP (v1) has a protocol id, channel, session, payload length, and
  a first/last message sequence. DEEP is aggregated: you get "price
  level update" (side, price, size) rather than individual orders.

  That means iex_builder.hpp is SMALLER than itch_builder.hpp: no
  order-id map, just apply level updates onto Book.

  The io layer owns pcap. Do not take a dependency on libpcap if you
  can avoid it; pcap and pcapng are simple enough to parse yourself,
  and Windows CI then has one fewer native dep. (If you use libpcap,
  document how Windows builds get Npcap.)


5.5 NORMALIZATION

  After both decoders work, introduce:

      using Event = std::variant<Add, Execute, Cancel, Delete,
                                 Replace, Trade, LevelUpdate>;

  Tools that do not care which exchange they are reading (mdstat
  across files, mdconvert to CSV) consume Event. The book builders
  can keep using the native handler for speed; normalization is for
  analysis, not for the parse-rate benchmark.


5.6 MAPPED FILES

  A full ITCH day is ~5-15 GB uncompressed. Do not read() it into a
  vector. Memory-map it.

      class MappedFile {
      public:
          explicit MappedFile(const std::filesystem::path&);
          std::span<const std::byte> bytes() const;
          // destructor unmaps  (RAII, lesson 10)
      };

  POSIX: open + mmap + munmap.
  Windows: CreateFileW + CreateFileMapping + MapViewOfFile + Unmap.

  One #ifdef in THIS file, nowhere else. The rest of the code sees a
  span. That is how you honor "Linux and Windows" without sprinkling
  OS checks through the parser.

6. CLI TOOLS (this is the intern half of the quote)
--------------------------------------------------------------------------------

Use CLI11. Every tool is a thin main() over the libraries. Flags are
consistent across tools: --symbol, --from, --to, --type, --limit.

  mdcat FILE
      Decode and print. Human table by default, JSON Lines with --json.
      Filters: --symbol AAPL --type A,E,X --from 09:30 --to 16:00
      --limit 20
      This is the "tcpdump of market data." Interviewers get this.

  mdstat FILE
      Counts by message type, first/last timestamp, peak msgs/sec in
      1-second buckets, sequence-gap count (IEX-TP), unknown-type count,
      bytes/sec. Exit code 1 if gaps > 0 (so it works in scripts).

  mdbook FILE --symbol AAPL --at 09:45:00.000
      Replay until that timestamp, print top N levels each side.
      --watch 1s prints a live-updating book as it replays (debug).

  mdconvert FILE --out out.csv --symbol AAPL
      One row per normalized Event. Later: Parquet via Arrow if you
      want to impress quants. CSV is enough for v1.

  mdbench FILE
      Parse-only (no book) and parse+book. Reports msgs/sec, GB/s,
      ns/msg. Release build, no sanitizers. This is the number you
      put in the README.

  mdreplay FILE --group 239.1.1.1 --port 18000     (stretch, sockets)
      Re-send a pcap onto a local UDP multicast group, original
      inter-packet timing or --asap. This is how firms test feed
      handlers without an exchange line.

  mdlisten --group 239.1.1.1 --port 18000          (stretch)
      Join the group, parse live, print with mdcat-like filters.
      Pair with mdreplay. Covers sockets + multithreading (listen
      thread, decode thread, a queue between them — lesson 11).

REST (the posting mentions it; keep it small):
  mdsnap --file FILE --port 8080
      Replay once into memory, then GET /book?symbol=AAPL returns
      JSON. cpp-httplib + nlohmann/json. This is NOT the hot path.
      It exists so you can say "I have called a REST service from
      C++ and also exposed one."

7. PYTHON BINDINGS
--------------------------------------------------------------------------------

Same pybind11 pattern as lesson 15, but the object is a feed, not a
matching engine:

    import mdkit

    for ev in mdkit.read("20240515.NASDAQ_ITCH50", symbol="AAPL"):
        if ev.kind == "add":
            ...

    book = mdkit.replay("...", symbol="AAPL", at="09:45:00")
    print(book.bids[:5], book.asks[:5])

  read() is an iterator so a 10 GB day does not become a Python list.
  Release the GIL around decode_stream (py::gil_scoped_release) so
  two threads can parse two files.

  This is how you talk to traders and quants in the interview: "the
  C++ library is the engine; Python is how research uses it."

8. TESTING STRATEGY (this is what makes it look professional)
--------------------------------------------------------------------------------

UNIT (Catch2, sanitizers ON)
  endian: known byte patterns <-> integers, including 48-bit
  itch decode: one test per message type, plus BadLength, UnknownType,
               truncated stream
  itch book: the prototype scenario above, plus:
               execute more than remaining
               replace of unknown ref
               two symbols (two locates) do not leak into each other
  iex decode: one IEX-TP packet fixture
  mapped_file: map a 64-byte temp file, compare bytes

GOLDEN FILES (checked-in binaries, tens of KB, not GB)
  tests/fixtures/itch_tiny.bin     produced by itch::encode
  tests/fixtures/iex_tiny.pcap
  mdcat --json fixture.bin | diff - expected.json

  The encoder lives in the library but is test-only (or a tools/
  helper). Never hand-edit binary fixtures.

FUZZ
  LLVM libFuzzer target: decode_stream on random bytes. Must not crash,
  assert, or leak (ASan). This is a strong interview talking point
  because feed data is hostile: truncated, wrong lengths, unknown types.

REAL-DAY SMOKE (not in CI by default; too big)
  scripts/smoke_day.sh downloads ONE Nasdaq sample (warn about disk:
  compressed files on emi.nasdaq.com are 3-12 GB) and runs
      mdstat file && mdbench file
  Document the URL and the expected ballpark counts in docs/specs.md.

PROPERTY
  encode(msg) then decode(bytes) == msg, for every type. The prototype
  encoder already exists for this.

9. PERFORMANCE TARGETS (so "low latency" is not a slogan)
--------------------------------------------------------------------------------

Measure parse-only and parse+book on a real ITCH day, Release, -O2,
no sanitizers, memory-mapped, no printing.

  Ballpark to aim for on a laptop (you will measure your own):
    parse-only     tens to hundreds of millions of msgs/sec is possible
                   with a tight visitor and no allocation
    parse+book     dominated by the unordered_map of live orders
                   (a busy symbol can have hundreds of thousands live)

  Optimizations, in order, after you have a number:
    1. Do not allocate per message. Handler takes const T&.
    2. orders_.reserve(1 << 20) before a day.
    3. books_ is a vector indexed by locate, not a map.
    4. Avoid std::string for symbols; Symbol is array<char,8>.
    5. Profile. On macOS: Instruments. On Linux: perf record.
       Only then consider a custom hash map.

  Put a table in the README:

      machine | file | msgs | parse-only | parse+book
      ...     | ...  | ...  | N msgs/s   | M msgs/s

  The lesson-14 matching engine did ~8e6 orders/sec. Parsing is
  cheaper than matching; if you are far below that, you are copying
  or printing too much.

10. CI AND PORTABILITY
--------------------------------------------------------------------------------

  .github/workflows/ci.yml
    jobs:
      linux:
        runs-on: ubuntu-latest
        steps: cmake -DMDKIT_SANITIZE=ON, build, ctest, then a
               Release build of mdbench on the tiny fixture
      windows:
        runs-on: windows-latest
        steps: cmake -DMDKIT_SANITIZE=OFF, build with MSVC, ctest

  That single file is how you prove "Linux and Windows" from the
  posting. Cross-compile from a Mac is optional; CI is the proof.

  Code rules for portability:
    - std::filesystem for paths
    - MappedFile is the only OS ifdef
    - no POSIX-only headers in libs/itch or libs/book
    - text fixtures use '\n', open files as binary
    - pack structs only via explicit byte loads, never #pragma pack
      across the wire (padding differs by ABI)

13. HOW YOU TALK ABOUT IT IN AN INTERVIEW
--------------------------------------------------------------------------------

  "I built a C++20 market-data toolkit. The library memory-maps a
   Nasdaq ITCH day, decodes length-prefixed big-endian messages with
   a visitor so the book builder is zero-virtual, and rebuilds every
   symbol's book from add/exec/cancel/replace. I added a second
   adapter for IEX DEEP, which is little-endian and market-by-price
   inside pcap, so the CLI tools speak one normalized event type.
   Tools are mdcat/mdstat/mdbook — the same class of utilities a
   feed-handler team uses to debug a bad day. It builds on Ubuntu

   bindings so you can iterate a day in a notebook without copying
   the data out of C++."

  project does not.
